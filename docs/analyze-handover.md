# 發射數據分析頁 — 交接說明

給要把這一頁併進其他站(例如 CalcMate)的人。程式碼在
`claude/posture-adjustment-aeb0qv` 分支。

## 檔案

| 檔案 | 內容 |
|---|---|
| `lib/shots.ts` | 分析核心。純函式、不碰 fs,瀏覽器端可跑 |
| `components/ShotAnalyzer.tsx` | `'use client'`,檔案上傳與全部 UI |
| `app/analyze/page.tsx` | 頁面外殼 + 方法說明 + 已知限制 |
| `app/layout.tsx` / `app/sitemap.ts` | 只各加了一行(導覽列連結、sitemap) |

## 這頁做什麼

使用者上傳 BeyGear App 匯出的備份 JSON,算出 App 介面上看不到的指標,
並用統計檢定判斷他改的動作有沒有效。

分成:總覽(SP 百分位、雜訊剔除)、三個隱藏指標、圈數 × 上升時間交叉表、
A/B 比較、跟別人對照。

**整份分析在瀏覽器裡跑,備份檔不上傳任何伺服器。** 這是刻意的,移植時請保留 ——
使用者的完整發射史是私人資料,沒有理由讓它離開他的裝置。

## 移植時需要知道的領域知識

這幾條是從 1,619 發真實資料裡驗證出來的,不用重新推導。

### 1. 每個取樣點 = 陀螺轉一圈

備份檔每一發帶 `rpms[]` 與 `times[]`。實測取樣間隔恰好等於 60000/rpm,
誤差 <1ms —— 感測器是每轉一圈記一筆。

因此:上升期的取樣點數 = 陀螺被帶動了幾圈(約當這一發用掉的繩長);
到峰值的時間 = 繩子帶動陀螺的實際時長。**這兩個量 App 介面上都沒有,
是這一頁的核心價值。**

### 2. 加速度沿用 App 自己的公式

`(峰值 rpm − rpms[1]) / (峰值時間 − times[1])`

反推自 App 畫面上顯示的數值,可以對到個位數。**不要換公式** ——
換了之後站上算的就跟使用者在 App 裡看到的對不起來,他會不信任這頁。

### 3. SP ÷ 加速度 ≈ 上升時間

分組平均的估計值與實際上升時間相差在數毫秒內。這條讓「只有一張截圖」
(SP 和加速度兩欄)也能跟別人放在同一把尺上比,不需要對方交出備份檔。

### 4. 雜訊門檻訂在「一圈增幅 0.5」,不要改成 P99

第 4 圈之後的每圈增幅:中位數 7.7%、P99 24.7%。

但門檻**不能**訂在 P99 附近:大約 5% 的紀錄會在**上升期最後一圈**出現
25–37% 的增幅,而且集中在第 11–13 圈、橫跨整段使用期間。那是繩子抽完前
最後一段不完整的圈被當成整圈計時造成的,是這個感測器的**系統性特性,
不是故障**。門檻訂在 P99 附近會誤殺 59 發正常球。

真正的跳點跟這群分得很開:一圈漲 50% 以上,最誇張的漲 3.3 倍而且下一筆
掉回三成。1,619 發裡只有 8 發。

### 5. A/B 用 Mann-Whitney,不用 t 檢定

每組只有十幾發時,一兩發好球就能把平均拉高。

實作有連續性校正,`z` 必須 clamp 到 0,否則兩組幾乎沒差時 p 會算出 1.03。
以 2000 次同分佈隨機樣本驗證,偽陽性率 4%(理論值 5%)。

## 技術相依

Next.js 14 App Router + React 18 + Tailwind。**沒有 API route、沒有資料庫、
沒有外部套件。**

用到的自訂色票在 `tailwind.config.ts`:`ink / panel / line / muted / brand /
good / warn / bad`。目標站的色票不同的話,`ShotAnalyzer.tsx` 裡的 className
要對應調整,其餘不用動。

## 一個設計決定,建議保留

**這頁刻意不給姿勢建議。**

網路上關於怎麼拉出高轉速的說法互相矛盾,而打到一萬五的玩家自己就說
「沒有一個所謂的最好拉的方式,因為每個人身高、臂展、協調度都不一樣」。
更關鍵的是:使用者花了兩週調整姿勢,1,619 發資料顯示 SP 與時間的相關
係數是 0.024 —— 完全沒有改變。

把猜出來的姿勢結論固化成工具,只會讓別人也花好幾個禮拜走冤枉路。
這一頁的定位是**給一把尺,讓使用者用 30 發自己驗證任何說法**,頁面上也
寫了這個理由。

要加內容的話,建議往「數據」加,不要往「教學」加。
